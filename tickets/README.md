## 派单顺序（每批最多 3 张，批内互不依赖）

| 批次 | Ticket | 内容 | 依赖 |
| --- | --- | --- | --- |
| 1 | T01 | 骨架与 pipeline 内核（含 demo 流水线、stub 模型、SQLite 迁移） | 无 |
| 2 | T02 | 账号数据复盘与周报 | T01 |
| 2 | T03 | 知识库（FTS5 + jieba + 引用） | T01 |
| 2 | T04 | 图文与海报渲染（Pillow + 声明式模板） | T01 |
| 3 | T05 | 选题与爆款对标 | T01（读 T02 写入的 post/metric） |

| 4 | T09 | Web 控制台 + 一键 demo + README | 全部 |

规则：

- **上游合并后才派下游**，否则 worker 从旧 HEAD 开工作区。
- 同批三张同时跑（`maxWorkers: 3`），慢活会占槽，所以同批不要放重活 + 重活。
- 一张工单一个 PR、一个分支；不合并、不关 issue。

## 每张工单的固定结构

1. 目标（做完之后，人能做什么原来做不了的事）
2. 依赖与前置
3. 可写路径（提示词级约束，宿主不拦，靠 PR 审阅兜底）
4. 非范围（明确不做的，防止范围膨胀）
5. 契约要点（引用 ADR 的条款，不重复抄）
6. 验收标准（可执行命令 + 可判定的输出）
7. 交付物清单
